# Нативный организатор файлов для macOS — спецификация релиза

Дата: 14 октября 2026 года. Статус: спецификация согласована пользователем 14 октября 2026 года; продуктовый код ещё не создаётся.

## Цель и подтверждённые требования

Дмитрий создаёт самостоятельный функциональный аналог Folder Tidy: полноценное настольное приложение с приятным нативным интерфейсом Apple, публичным репозиторием GitHub и установочными сборками для других пользователей. Процесс использует Superpowers и релевантные инструкции Everything Claude Code (ECC).

Успех означает, что пользователь скачивает приложение, выбирает папки и правила, просматривает план, сортирует реальные файлы и может восстановить их расположение после перезапуска. Рабочее название проекта — TidyFolder; окончательное название и иконка определяются до публичного релиза. Базовая лицензия исходников предлагается MIT. Приложение работает локально; аккаунт и сервер для сортировки не требуются. Русский и английский интерфейсы входят в релиз.

## Выбор технологии

| Вариант | Преимущества | Ограничения | Решение |
| --- | --- | --- | --- |
| SwiftUI + AppKit + Foundation | Нативные элементы, Finder, метаданные macOS, небольшой runtime | Только macOS; сборки и подпись требуют инструментов Apple | Рекомендуемый вариант |
| Tauri + Rust + web UI | Возможность будущей поддержки Windows/Linux | Дополнительный мост к macOS; нативный интерфейс требует ручной адаптации | Резерв, если появляется требование других ОС |
| Electron | Быстрая web-разработка, общая кодовая база | Более тяжёлый runtime; больше работы для нативного поведения | Не выбирается для данного запроса |

Предлагаемая минимальная ОС — macOS 14. Язык — Swift 6.2. UI использует SwiftUI; AppKit подключается для выбора папок, Finder, меню и необходимой системной интеграции. Движок отделяется от UI в тестируемый Swift Package. Apple Silicon проверяется локально; Intel включается в совместимость только после сборки и проверки соответствующего артефакта.

Текущая среда: macOS 15.7.1, arm64, Swift 6.2 и Command Line Tools. Полный Xcode сейчас отсутствует. Необходимые для UI-тестов возможности проверяются отдельно; отсутствие тестового запуска не считается успешной проверкой.

## Функциональный объём

Полная совместимость определяется явной матрицей документированных возможностей Folder Tidy 2.9.7. Сайт сообщает 22 встроенных правила; руководство описывает более раннюю версию и 20 правил. Перед объявлением полной совместимости список категорий и семантика спорных настроек сверяются по актуальному оригиналу/его публичным материалам. Несверенные детали отображаются в отчёте совместимости как несверенные.

| Возможность | Поведение нашего приложения | Критерий проверки |
| --- | --- | --- |
| Источник и назначение | Системный выбор папок, drag-and-drop; сортировка в исходной папке или другой выбранной папке | Предпросмотр показывает фактические исходные и конечные пути |
| Встроенные правила | Категории по UTType и дополнению расширениями; каталог учитывает Markdown, eBook, 3D и saved email из release notes | Фикстуры основных и актуальных категорий; отдельный отчёт сверки |
| Пользовательские правила | Имя, расширение, тип, размер, даты создания/изменения и теги Finder; текстовые и числовые операторы | Положительные, отрицательные и граничные примеры для каждого оператора |
| Составные условия | Вложенные группы «все», «любое», «ни одно» | Однозначная сериализация и логические таблицы тестов |
| Порядок правил | Перетаскивание; первое совпавшее включённое правило определяет назначение | Один файл получает не более одного перемещения |
| Включение правил | По одному и массово; специальные правила папок/aliases включаются явно | Состояние сохраняется после перезапуска |
| Подпапки назначения | Правило допускает относительный путь внутри выбранного назначения | Абсолютные пути, пустые компоненты и выход через `..` отклоняются |
| Исключения | Выбранные файлы и целые деревья папок | Исключённые объекты не попадают в операции |
| Рекурсивная сортировка | Включаемая обработка подпапок; ссылки не используются для обхода дерева | Нет циклов и повторного сканирования выходных папок |
| Папки, aliases и packages | Пустые папки и aliases имеют отдельные правила; содержимое bundles по умолчанию не раскрывается | `.app`, `.framework`, `.xcassets` и документные packages сохраняют целостность |
| Теги Finder | Разрешить/пропустить помеченные объекты; свойства тегов в правилах | Поведение сверяется с оригиналом, русский UI не повторяет двусмысленный текст старого руководства |
| Очистка пустых папок | По настройке; удаление только учтённых пустых каталогов, сохранение структуры для undo | Каталоги с посторонними файлами не удаляются |
| Скрытое содержимое | Защищённые/исключённые деревья не трогаются; для выбранной очистки метаданные и скрытые объекты сохраняются в служебный staging | Undo возвращает скрытые объекты; активные репозитории и данные приложения защищены |
| Папка с датой запуска | Опциональная верхняя папка с именем источника и timestamp | Повторные запуски получают различные назначения |
| Прогресс и отмена | Число обработанных/перемещённых/пропущенных файлов; отмена на безопасной границе | После отмены доступны история и undo выполненных операций |
| История и undo | Сохранённые запуски, подробности, восстановление после перезапуска | Приложение возвращает только собственные учтённые объекты и не удаляет новые пользовательские файлы |
| Finder и диагностика | Показ назначения в Finder; дополнительный локальный лог по настройке; опциональное скрытие других окон перед запуском | Нет необходимости запрашивать автоматизацию Finder ради обычного открытия папки |
| Предпросмотр — дополнение | План операций и причин пропуска до перемещения | Сканирование ничего не меняет; изменившиеся файлы перепроверяются при выполнении |
| Конфликты — дополнение | По умолчанию пропуск; опция «сохранить оба» с новым именем | Существующий файл никогда не перезаписывается автоматически |

Фоновое наблюдение за папками, AI-классификация, подписки, Windows и облачный backend не входят в релиз 1.0. Их появление является отдельным изменением требований, а не условием реализации данного аналога.

## Интерфейс и основные сценарии

Основное окно ориентируется на Finder и системные настройки: sidebar «Сортировка / Правила / История», компактный toolbar и рабочая область. Размер по умолчанию около 1080 × 720, интерфейс сохраняет читаемость от 820 × 560. Шрифты и размеры текста используют системные стили; SF Symbols, системный акцент, стандартные focus rings, меню и горячие клавиши. Светлая/тёмная темы следуют системной настройке; декоративные эффекты не подменяют доступность на macOS 14/15.

Сортировка: выбор источника и назначения → настройки запуска → «Предпросмотр» → таблица файлов, категорий, путей и предупреждений → «Сортировать» → прогресс с отменой → итог и «Восстановить». Изменение правил или папок делает предыдущий план недействительным.

Правила: список с переключателями и перетаскиванием; редактор в sheet с названием, папкой назначения, группами условий и тестовым совпадением. Встроенные правила доступны для включения и изменения приоритета; редактирование их внутренних условий не требуется для совместимости.

История: время, источник, назначение, результат и состояние восстановления. Детали показывают ошибки и конфликты. После аварийного завершения приложение показывает незавершённый запуск и позволяет восстановить выполненные операции; автоматическое продолжение перемещений не происходит.

Доступность: полное управление клавиатурой, VoiceOver labels, поддержка Reduce Motion, отсутствие информации только через цвет. Локализация касается UI; переименование уже созданных каталогов при смене языка не выполняется.

## Архитектура и договоры модулей

| Модуль | Ответственность | Контракт |
| --- | --- | --- |
| Domain / RuleEngine | Типизированные условия, сравнение и приоритеты | Метаданные + правила → совпадение и причина; без файловых изменений |
| Scanner / Planner | Обход выбранного дерева, классификация, резервирование назначений | Настройки + снимок файлов → неизменяемый план |
| FileSystem adapter | Реальные file APIs и управляемые тестовые ошибки | Проверка идентичности, no-clobber move/copy, attributes, tags, ресурсы тома |
| ExecutionCoordinator | Единственный активный изменяющий запуск, прогресс и отмена | План → поток событий и итог; тяжёлый I/O вне MainActor |
| JournalStore | Долговечное состояние операций и миграции | Транзакционные изменения состояния, история и recovery |
| Recovery / Undo | Сверка журнала с диском и безопасное восстановление | Запуск → отчёт restored/skipped/conflict/missing |
| SettingsStore | Правила, настройки и выбранные папки | Версионированный JSON с атомарной заменой; bookmarks при наличии sandbox |
| Presentation | SwiftUI views и state на MainActor | Отображение состояния и пользовательские команды без встроенного файлового движка |

Журнал использует системную SQLite с WAL и `synchronous=FULL`; применимость `fullfsync` проверяется для macOS. Фактические guarantees проверяются экспериментами с аварийным завершением, а не выводятся из названия технологии. Данные живут в Application Support приложения; лог содержит локальные пути только локально и не отправляется автоматически. Run gate явно защищает sorting/undo от одновременного запуска, включая actor reentrancy.

RuleGroup содержит mode (all/any/none) и дочерние группы/условия. FileSnapshot содержит URL, ресурсный идентификатор, идентификатор тома, тип, размер, timestamps, package/symlink/cloud flags и нужные метаданные. PlannedOperation содержит ID, источник, назначение, правило и ожидаемый snapshot. RunRecord хранит настройки/версию схемы/правил, timestamps и итог. OperationRecord хранит intent, фактические пути и состояние операции. Идентификаторы файлов не используются как единственная проверка содержимого.

## Инварианты файловых операций

1. Предпросмотр не меняет пользовательские файлы. Пустой план не создаёт запись успешной сортировки.
2. Перед каждым перемещением проверяются существование, ожидаемая идентичность/метаданные, границы путей и конфликт назначения. Изменившийся объект пропускается с объяснением.
3. До первой мутации intent записывается в долговечный журнал. Основные состояния: prepared → copying → verified → committed → sourceRemoved → completed. Intent предшествует каждой мутации; outcome записывается после неё. SQLite и filesystem не имеют общей транзакции: recovery сверяет фактические файлы с записью и сохраняет неоднозначные объекты.
4. Внутри одного тома используется атомарное перемещение без перезаписи через exclusive rename, а не связка exists-check и обычного rename. Неподдерживаемый том получает явный результат unsupported вместо ослабления гарантии. Для разных томов: эксклюзивно созданная служебная копия в целевом каталоге → проверка данных/метаданных и синхронизация → атомарная exclusive публикация → запись результата → удаление источника. Каждая граница допускает сбой; recovery отличает источник, служебную копию и опубликованную копию. Пока источник сохраняется, результат называется «Скопировано; источник сохранён», а не «Перемещено».
5. Проверка межтомовой копии включает потоковое сравнение хеша и сохранение необходимой metadata/resource forks; источник не удаляется при провале проверки. Повторная проверка источника перед удалением исключает уничтожение изменившегося файла.
6. Выходная папка внутри источника исключается из обхода целиком. При сортировке в том же корне защищаются целевые подпапки; относительные пути сверяются по компонентам, а не строковым префиксом.
7. Symlinks не разыменовываются при обходе. Alias/ссылка перемещается как самостоятельный объект только при явном правиле; назначение проверяется на выход через существующие symlinks.
8. Облачные placeholders по умолчанию пропускаются с причиной. Приложение не обещает прозрачную работу с нескачанным содержимым и не запускает загрузку без действия пользователя.
9. Undo записывает обратные операции в тот же долговечный журнал. Он не перезаписывает занятой исходный путь и не перемещает объект, который не удаётся однозначно сопоставить с записью. Изменённые, заменённые и неоднозначные объекты по умолчанию остаются на месте с конфликтом; пользователь сначала разрешает конфликт вне автоматического восстановления.
10. Созданные каталоги удаляются при undo только если их принадлежность запуску учтена и они действительно пусты. Скрытые и посторонние объекты не уничтожаются ради удаления каталога.
11. Отмена останавливает выдачу новых операций; текущая операция завершается до безопасной границы. Один процесс и одно хранилище не запускают одновременно sorting и undo.
12. Недостаток места, права, отключение тома и недоступное хранилище журнала возвращаются пользователю как конкретный результат. Невозможность надёжно записать журнал останавливает новые изменения. Координация файлов применяется для поддерживающих её приложений/провайдеров; абсолютная защита от любого стороннего процесса, одновременно изменяющего исходный файл, не заявляется.

## Доступ к папкам и выпуск

Первый релиз распространяется напрямую через GitHub Releases. Доступ задаётся выбором папок через NSOpenPanel; полный доступ к диску не является условием запуска. Приложение уважает системные TCC permissions. App Sandbox и bookmark permissions оцениваются отдельно при выборе sandboxed-сборки; политика не смешивает произвольные URL с разрешёнными security-scoped ресурсами.

Репозиторий содержит исходники, README на двух языках, лицензию, руководство сборки, матрицу совместимости, changelog, issue templates, тесты и workflow CI. Рабочий GitHub-аккаунт подтверждается как `dmsznv-dot`; пользователь создаёт публичный репозиторий `dmsznv-dot/tidyfolder`.

CI проверяет core tests и сборку приложения. Release workflow получает тег версии, создаёт `.app`, ZIP для скачивания и SHA-256; DMG добавляется как удобный установочный формат. Публикация имеет отдельную финальную проверку состава артефактов, версии и результата CI.

Подпись Developer ID, Hardened Runtime, notarization и stapling поддерживаются в release pipeline. Для подписанного публичного релиза необходимы реальные сертификат и доступ Apple Developer. Наличие этих данных пока не подтверждено. При их отсутствии допустима отдельно обозначенная unsigned preview; её нельзя представлять как проверенный нотарифицированный релиз. Сертификаты и пароли поступают через secrets CI, не через git.

Первый релиз проверяет обновления через страницу GitHub Releases по команде пользователя; автоматическая установка обновлений не входит в 1.0. Поддержка Intel или другой версии ОС объявляется только после соответствующей проверки.

## Проверки и критерии приёмки

Правила проверяются unit-тестами на граничных размерах/датах, регистрах имён, UTType, вложенных группах и стабильном приоритете. Парсинг и миграции настроек проверяются на повреждённых и более новых форматах.

Файловые интеграционные тесты используют временные каталоги и фиксированные fixtures. Обязательны: sort → restart → undo; конфликты sort и undo; два одинаковых имени; Unicode; case-insensitive volume; nested destinations; отсутствующий источник; изменение файла после preview; symlink cycle/escape; package contents; скрытые файлы; сохранение тегов и metadata; read-only errors; отмена; повторное восстановление; аварийный выход после каждого существенного шага журнала.

Межтомовой перенос проверяется на двух отдельных тестовых томах либо явно остаётся неподтверждённой совместимостью. Ошибки диска и журнала также моделируются через FileSystem/Journal protocols; моделирование не заменяет проверку настоящего межтомового переноса.

UI проходит ручной запуск на macOS 15.7.1: выбор папок, drag-and-drop, редактор и приоритеты, preview, cancel, история и undo, темы, keyboard и VoiceOver. UI automation выполняется при наличии полноценной среды Xcode; её отсутствие отражается в отчёте.

Нагрузка: фиксированный набор 10 000 небольших файлов на локальном SSD. Измеряются время сканирования, перемещения, undo и память с указанием машины и режима журнала. Цель — отзывчивый UI и отсутствие неограниченной параллельной выдачи I/O; скорость оригинала не заявляется до измерений. Любое ускорение сохраняет инварианты журнала и восстановления.

Версия 1.0 готова, когда функциональная матрица имеет проверенный статус для всех заявленных возможностей, core tests и сборки проходят, crash/undo проверки не теряют данные, native UI проходит проверку, документация установки соответствует реальному артефакту, а подписанные и неподписанные сборки обозначаются честно.

## Применение Superpowers и ECC

Superpowers задаёт порядок: спецификация → её согласование → детальный план и выбор исполнения → TDD/реализация → code review → проверка готовности. Спецификация согласована; сейчас рассматривается план реализации, scaffolding и продуктовый код не создаются.

ECC architect используется отдельным агентом для проверки границ модулей, вариантов и failure modes; его рекомендации включены в этот проект. ECC planner применяется при следующем этапе планирования. ECC code-reviewer проверяет фактические изменения, тесты и регрессии. ECC security-reviewer адаптируется к файловым путям, permissions, журналу и release secrets; нерелевантные web/npm проверки не запускаются. Swift concurrency, actor persistence и protocol DI testing читаются перед соответствующей реализацией. Это применение выбранных оригинальных инструкций; глобальная установка ECC и его hooks не выполнены.
